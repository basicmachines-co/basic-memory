# Basic Memory 1.0 working migration guide

This is the working change list and migration guide for 1.0. It covers the new
tool contracts and the corresponding changes to agents, integrations, tests, and
documentation. Add migration decisions and verified instructions as release work lands.
Each section distinguishes implemented development work from planned release work;
neither implies that the current published release includes the change.

## Cloud transfers: replace sync and bisync with push/pull

**Status:** planned for v1.0; implementation tracked in
[#1845](https://github.com/basicmachines-co/basic-memory/issues/1845).
This completes the deprecation introduced through
[#1596](https://github.com/basicmachines-co/basic-memory/issues/1596).

### What is being removed

- `bm cloud sync`: destructive one-way mirroring from local files to Cloud.
- `bm cloud bisync`: bidirectional mirroring.
- `bm cloud bisync-reset`: initialization/reset of bisync state.

The plan is to retain migration-only stubs for these command names in 1.0. They will
exit nonzero with replacement instructions and perform no transfers or deletions.
They will not silently invoke push or pull.

### Why

Cloud notes can be created and edited by people and managed agents independently of
your local folder. The old `sync` command makes Cloud match that folder, deleting
cloud-only files and files excluded by the local `.bmignore`. A local copy should
not silently erase knowledge created in Cloud.

Push/pull provide explicit directional transfers on both Personal and Team
workspaces. They preserve files found only on the destination and surface differing
content for an explicit choice.

### Replacement commands

Download Cloud files into the configured local folder:

```bash
bm cloud pull --name research --dry-run
bm cloud pull --name research
```

Upload local files to Cloud:

```bash
bm cloud push --name research --dry-run
bm cloud push --name research
```

Use `--workspace <workspace-slug>` when the project name is ambiguous. Existing
local path configuration remains useful. `bm cloud sync-setup` is not being removed
by this change: it configures that path, rather than running the legacy mirror.
Personal transfers still use shared rclone setup; Team transfers use WebDAV with
project-level authorization and do not require rclone setup.

### Resolve differing files explicitly

By default, a transfer aborts before copying anything if it finds conflicting files
or cannot compare files. It lists conflicts so you can inspect them and choose:

| Option | On push | On pull |
| --- | --- | --- |
| `--on-conflict fail` (default) | Abort on differing files | Abort on differing files |
| `--on-conflict keep-local` | Replace differing Cloud files with local content | Leave differing local files untouched |
| `--on-conflict keep-cloud` | Leave differing Cloud files untouched | Replace differing local files with Cloud content |
| `--on-conflict keep-both` | Save incoming local content as a conflict copy in Cloud | Save incoming Cloud content as a conflict copy locally |

These choices apply to differing files; new source files are still transferred.
Conflict copies use a `.conflict-<date>` suffix before the file extension.

For an intentional local-authoritative upload, preview first:

```bash
bm cloud push --name research --on-conflict keep-local --dry-run
bm cloud push --name research --on-conflict keep-local
```

This preserves cloud-only files. It is **not** an exact-mirror replacement for
`cloud sync`.

To download and preserve both versions of differing files:

```bash
bm cloud pull --name research --on-conflict keep-both --dry-run
bm cloud pull --name research --on-conflict keep-both
```

### Important differences from mirroring

- **Deletions do not propagate.** Deleting a local file does not delete its Cloud
  copy; deleting a Cloud file does not delete its local copy. A later transfer in
  the reverse direction can copy that file back.
- **Renames are not tracked as moves.** The new path may transfer while the old
  destination path remains. Review and remove obsolete copies explicitly.
- **There is no shared sync baseline.** Any differing content is a conflict, even
  when only one side was edited. These commands do not perform Git-style
  three-way merges or automatically choose the newest version.
- **Pull followed by push is not bidirectional mirroring.** It does not propagate
  deletions or resolve divergent content automatically.
- **Ignore rules do not clean up previous uploads.** For Personal workspaces,
  `bm cloud prune --name research --dry-run` previews Cloud files matching local
  `.bmignore` rules. Running it without `--dry-run` requests confirmation before
  deletion. This is targeted cleanup, not general mirror deletion.

### Updating scripts and scheduled jobs

1. Find calls to `cloud sync`, `cloud bisync`, and `cloud bisync-reset` in scripts,
   scheduled tasks, and personal instructions.
2. Choose the intended direction: push for uploads, pull for downloads. If both
   are needed, account explicitly for conflicts and the lack of deletion tracking.
3. Preview with `--dry-run`. With conflicts, select a strategy before previewing
   the resolved transfer; dry-run does not bypass conflict checks.
4. Use the default conflict failure unless the workflow deliberately chooses a
   winning side. Monitor nonzero exits rather than silently discarding them.
5. Handle intentional deletion or rename cleanup separately, after reviewing the
   affected files. Do not assume a missing local file authorizes Cloud deletion.

The removal must not automatically delete local files, Cloud files, credentials,
or old bisync state directories. Existing backups and snapshots remain independent
of transfer commands. Removing `cloud check` is outside this migration's scope.

## MCP tools: migrate to the bm_* surface

**Status:** implemented on the development branch for 1.0 (SPEC-35.2). Upgrade your
server and its agent packages together, then restart clients to refresh cached tool
schemas and permission lists. Legacy MCP registrations are removed immediately,
with no compatibility aliases or transition window.

`bm tool` mirrors the 1.0 tools: one subcommand per `bm_*` tool, flags named after the
tool's parameters in kebab case, and the same Pydantic validation an MCP client gets.
Output is the tool's text result, or its JSON result with `--json`. `bm tool` no longer
switches to JSON when piped, and `--plain` and the Rich renderers are gone; scripts
pass `--json`. Without `--project`, commands use the configured default project.

| Previous CLI | 1.0 CLI |
| --- | --- |
| `write-note`, `write --title T --folder F --type X` | `write --title T --directory F --note-type X` (or `--identifier path.md`) |
| `read-note`, `read --frontmatter` | `read` (frontmatter is now included by default) |
| `read` (body only, the old default) | `read --no-include-frontmatter` |
| `edit-note`, `edit --operation OP` | `edit --command OP` |
| `delete-note`, `delete ID --is-directory` | `delete --identifier ID`, or `delete --path DIR --recursive` |
| `search-notes`, `search --vector/--hybrid/--title/--permalink` | `search --mode semantic/hybrid/title/permalink` |
| `search --meta k=v`, `--filter JSON`, `--tag`, `--status` | `search --filters JSON` |
| `search --type T`, `--entity-type K`, `--after_date D` | `search --note-types T`, `--items K`, `--since D` |
| `build-context`, `context URL --timeframe D` | `context IDENTIFIER --since D` |
| `recent-activity`, `recent` | `project recent` |
| `list-projects`, `projects` | `project list` |
| `list-workspaces`, `workspaces` | `project list` (omits workspaces with no projects), or `bm cloud workspace list` for every workspace |
| `schema-validate`, `schema-infer`, `schema-diff`, `validate`, `infer`, `diff` | `schema validate/infer/diff`; a positional `TYPE` becomes `--note-type TYPE` |
| `validate path/note.md` | `schema validate --identifier path/note.md` |
| `--project-id UUID` | `--project UUID` |
| (new) | `move`, `list`, `find` |

The bundled manual page `tools-migration(7)` (`bm man tools-migration`) carries both tables.

| Previous MCP tool | 1.0 replacement |
| --- | --- |
| `read_note`, `read_content`, `view_note`, `cat` | `bm_read` with explicit line bounds where needed |
| `write_note` | `bm_write` |
| `edit_note` | `bm_edit` |
| `search_notes`, `grep` | `bm_search` |
| `build_context` | `bm_context` |
| `list_directory`, `ls` | `bm_list` for one level; `bm_find` for recursive inventory |
| `find` | `bm_find` |
| `recent_activity` | `bm_project(command="recent")` |
| `tail` | `bm_project(command="recent")`; map `timeframe` to `since` and `lines` to `page_size`. Recent JSON includes `created_at`, not `updated_at`; shell users needing the last-change timestamp can use `bm tail --json`. |
| `list_memory_projects` | `bm_project(command="list")` |
| `list_workspaces` | `bm_project(command="list")` groups projects by workspace, so it omits a workspace with no projects; `bm cloud workspace list` in a shell lists every workspace |
| `create_memory_project` | `bm_project(command="create", name=..., path=...)` |
| `delete_project` | `bm_project_delete` (opt-in) |
| `schema_validate`, `schema_infer`, `schema_diff` | `bm_schema(command="validate"/"infer"/"diff")` |
| `move_note` | `bm_move` |
| `delete_note` | `bm_delete` |
| `man` | `bm_man` |

### Tool-by-tool change list

The primary surface has twelve tools, plus the separately enabled destructive
`bm_project_delete` operation. The registry in
`src/basic_memory/mcp/tools/__init__.py` and installed manuals are authoritative.

| Tool | Capabilities and migration details |
| --- | --- |
| `bm_read` | Exact note/file reads, with line, section, and token-budget bounds. Missing targets are refusals; callers must search separately instead of relying on fuzzy read fallback. JSON includes revision metadata. |
| `bm_write` | Create notes or explicitly overwrite an existing target. Guard overwrites with `expected_checksum`; consume the compact change receipt. |
| `bm_edit` | Incremental edits and frontmatter changes selected by `command`. A missing note is refused, not created. |
| `bm_delete` | Delete a note through `identifier`, or a directory through `path` with `recursive=True`. Remove the old `is_directory` argument; locked-note protection still applies. |
| `bm_move` | Move a note or directory to `destination`. A trailing slash means move into that directory under the source's existing name; without it, the destination is the new path. |
| `bm_search` | Ranked text, title, permalink, semantic, or hybrid search; metadata filters; project scopes; and matching-line searches. Replaces both note search and the MCP grep workflow. |
| `bm_context` | Build graph context from an exact `identifier`, with bounded depth and time window. Whitespace-only identifiers are refused. |
| `bm_list` | List one directory level in the required project. `/` is that project's root; discover projects with `bm_project(command="list")`. |
| `bm_find` | Recursive file discovery with path and frontmatter filters. Use this for inventory rather than expecting recursive `bm_list` results. |
| `bm_project` | Consolidate `list`, `create`, and `recent`. Project rows carry workspace metadata; deletion is not a command on this tool. |
| `bm_project_delete` | Separate, opt-in destructive project deletion. Keep it separate in tool permissions and agent allowlists. |
| `bm_schema` | Consolidate schema `validate`, `infer`, and `diff` behind `command`. |
| `bm_man` | Discover, read, or search installed manuals. Supply a page or a query, not both; no project selection is required. |

### Change arguments and response handling too

- Pass names, workspace-qualified names, or external UUIDs through required `project`.
  Remove `project_id`; calls do not retain a selected project between requests.
- Search uses `mode`, `filters`, `items`, `since`, and `all_projects` instead of
  `search_type`, `metadata_filters`, `entity_types`, `after_date`, and
  `search_all_projects`. Use `items=["note"]` for whole notes. Put `tags` and
  `status` inside `filters`; `note_types` still filters frontmatter types.
- Edit uses `command` instead of `operation`. `set_metadata` edits frontmatter;
  edits never create missing notes.
- Context uses `identifier` instead of `url` and `since` instead of `timeframe`.
  It defaults to JSON and a seven-day window. Depth is bounded to 1–5.
- Recent activity uses `command="recent"` and `since`. JSON returns an object
  with `results` and paging fields, rather than a bare array.
- Project discovery returns project rows with workspace fields. It does not return
  the old standalone workspace role/subscription response.
- Reads use `start_line`, `end_line`, `section`, or `max_tokens`; `page` and
  `page_size` do not slice note content. JSON reads include frontmatter by default;
  pass `include_frontmatter=False` when a consumer needs the body alone.
- Move uses `destination`. End a folder destination with `/` to preserve the file
  name. JSON move/delete receipts identify success through `action` (`moved` or
  `deleted`), rather than boolean `moved`/`deleted` fields.
- Refusals set MCP `isError`. JSON error text contains `error`, `message`, and
  sometimes `try_instead`. Handle `NOT_FOUND`, `ALREADY_EXISTS`, and
  `REVISION_CONFLICT`; do not treat them as successful empty results or expect
  legacy `NOTE_*` payload fields. Read again to obtain the current checksum.

For an overwrite, prefer the exact returned `file_path` as `identifier` and pass
`expected_checksum` from a fresh read. Do not reconstruct a filename from a title.

```python
note = await bm_read(identifier="notes/Plan.md", project="research", output_format="json")
await bm_write(
    identifier=note["file_path"],
    content="Updated plan.",
    overwrite=True,
    expected_checksum=note["checksum"],
    project="research",
)
await bm_search(filters={"status": "active", "tags": ["planning"]}, project="research")
await bm_project(command="recent", since="7d", project="research", output_format="json")
```

### Update callers and installed instructions

Update custom agents, hooks, MCP allowlists, tool routers, recorded request fixtures,
and test fakes as well as prompts and skills. Native Hermes and OpenClaw wrappers
may retain their host-facing arguments while translating to the new MCP contract.
Tau preserves the core `bm_` prefix; there is no `bm_bm_write` tool.

Use `bm_man(page="bm-search(3)")` or `bm man bm-search` for the installed reference.
Re-run benchmark baselines after upgrading; historical results describe the tool
surface they were measured against and should not be relabeled as 1.0 results.

### Project routing and refusal handling

- Core note, folder, context and schema calls require a nonempty `project`,
  including single-project sessions, constrained servers and qualified targets.
  Discovery (`bm_project(command="list")`) and bundled manuals need no project.
  `bm_project(command="recent")` requires `project` too.
- Search requires explicit scope: `project` for one project, `projects` for
  selected projects, or `all_projects=True` for all accessible projects. A
  project-qualified path or memory URL does not replace explicit search scope.
- A relative path such as `notes/topic.md` does not select a project merely
  because it contains a slash. Pass scope with every call; qualified identifiers
  must agree with that scope. Restart MCP clients to refresh required parameters.
- Search resolves project-qualified `memory://` URLs without rewriting stored
  project-qualified permalinks into workspace-qualified identities.
- Native ChatGPT search/fetch and saved search/continue prompts resolve their
  selected/default project before calling the stricter core tools. Qualified
  fetch targets still select the project they name.
- Mutation receipts replace prose/footer parsing. Use `action`, `file_path`,
  `permalink`, and `checksum` where returned; moves include `previous_file_path`.
- Handle `LOCKED`, `INVALID_ARGUMENTS`, `OUTSIDE_PROJECT`, and other typed
  refusals as errors. An absent checksum does not prove a note was deleted.
  For `OUTCOME_UNKNOWN`, read back the target before retrying a mutation.

  This does not remove the separately supported hosted MCP App interface.

[#1833](https://github.com/basicmachines-co/basic-memory/issues/1833). Old manual
URLs provide retirement notices pointing to current replacements. Run local
diagnostics with `bm doctor`. Native host wrapper interfaces and separately

### Python 3.15: blocked by ONNX Runtime

Python 3.15 is released, but Basic Memory's default installation depends on
`fastembed`, which depends on `onnxruntime` for local model inference. On 2026-10-24,
installing the locked dependencies with Python 3.15.1 failed because ONNX Runtime
1.27.0 has no compatible wheel or source distribution. The latest ONNX Runtime
1.31.0 also has no Python 3.15 wheels; updating FastEmbed from 0.8.0 to 0.9.0 does
not remove that dependency. The separate `onnx` model-format package is not a
replacement for ONNX Runtime.

Track [upstream Python 3.15 wheels](https://github.com/microsoft/onnxruntime/issues/33271).
Keep Python 3.12–3.14 in the supported test matrix and use Python 3.14 for local
development. Local embeddings remain part of the default installation; do not
silently disable them to claim Python 3.15 support.

Before enabling 3.15:

- [ ] Verify published ONNX Runtime wheels for the supported operating systems.
- [ ] Refresh the lockfile and verify a complete runtime/dev installation on 3.15.
- [ ] Run real local-embedding, SQLite, PostgreSQL, MCP, and package checks.
- [ ] Add Python 3.15 to CI and update the documented support range.
